# 一攻一防调试记录：2026-11-19

本轮只调整 Football Simulation 的二维版本，未修改三维工程。调试前状态为本仓库提交 `f4b67fc`；基线程序、候选程序、固定开局及测量结果保存在 `verification/defence-tuning-20261119/`。

## 如何使用

从仓库根目录运行：

```bash
python 2D_Shared_Policy_2026-11-11/server.py --open
```

Windows 可以完整解压实时版 ZIP，双击 `start_windows.bat`。需要先关闭旧服务再启动；刷新网页不会重新导入 Python 模块。

页面默认 8 倍播放。展开 **Spawn rectangles / 出生矩形区域**，可以输入双方的 x、y 边界，也可以暂停后在 **Drag on pitch / 在球场上拖动** 中选择红方或蓝方，在球场上拖出矩形。拖动中的黄色框是预览，松开后生成新开局。

提供中场、门前、边路预设。坐标以场地中心为原点，向右、向上分别为 x、y 正方向，单位为米。默认范围：

| 对象 | x 范围 | y 范围 |
| --- | --- | --- |
| 红方 | −1.0～1.0 | −1.1～1.1 |
| 蓝方 | 1.8～3.2 | −1.25～1.25 |

足球在进攻球员脚前生成。蓝方到右侧球门中心的距离必须比红方和足球都至少短 0.25 米。两个人和足球出生时不能重叠。采样只在选定矩形内进行；无法满足约束时返回错误，保留之前的场景，不采用越界放置作为后备方案。矩形内的候选点按均匀分布采样，再筛选满足这些条件的组合，所以最终分布是有条件的。

当前会话中，随机新开局和批量测试会保留选定范围。修改实时版目录下的 `spawn_zones.json` 可设置下次启动时的默认范围。文件的每组四个数字依次为 x 最小值、x 最大值、y 最小值、y 最大值。固定场景使用各自的固定位置，不使用随机矩形。

## 转身为什么慢

当前执行模型把转向、前进、后退和侧移分别执行。转向率沿用历史单动作测试的平均值，约每秒 4.2～4.3 度；转 90 度就需要约 21 秒模拟时间。后退约 0.034 m/s，也慢于前进约 0.085 m/s。

因此，当进攻方已经完全越过防守方、继续同向推进时，立即后退或者先转身都不能保证追回。本轮没有凭空提高转向速度，也没有新增未经验证的“边走边转”步态。主要改善方式是在被突破之前选好拦截位置。

## 保留的策略改动

1. 搜索未来球路上的可到达位置，未来时间采样间隔不超过 0.75 秒，比原先固定 21 个采样点更细。
2. 截球身体位置设置在预测足球的球门侧约 0.30 米处，为来球留下封堵余量；仍通过普通移动和脚部接触执行。
3. 常规拦截目标约每 0.6 秒刷新；足球移动超过 0.18 米时提前刷新，减少微小位置变化引起的目标切换。
4. 被突破后，目标改为球门通道，按已知前进、后退、侧移和转向速率比较路径耗时，选择较快的第一步动作，避免一直追逐持球队员脚前一个无法赶上的点。
5. 实时版本始终导入自己的 `backend/`，不再自动切换到相邻三维工程的模块。

红方的进攻决策、双方运动速度、起脚时间、接触计算和进球判断保持不变。没有给蓝方额外速度、额外触球范围或预设胜负。

## 对照方式

候选筛选使用种子 347～496，共 150 个固定矩形开局。四轮共比较 25 组参数，另有一组初步候选测试。选定后，用此前未用于候选筛选的种子 5000～5999 做最终对照，每局最多 180 秒模拟时间。

最终对照将同一份出生位置、朝向和种子分别交给调试前程序和选定程序。出生范围改变本身会显著影响结果，因此没有把“旧出生方式”和“新出生方式”的差异算成策略改进。

## 1,000 次最终对照

| 观察项 | 调试前 | 调试后 |
| --- | ---: | ---: |
| 红方进右门 | 311（31.1%） | 253（25.3%） |
| 蓝方将球推进左门 | 595（59.5%） | 665（66.5%） |
| 超时 | 87 | 78 |
| 出界 | 7 | 4 |
| 出现完成解围事件的局数 | 596 | 660 |
| 出现有脚部证据、球向左推进至少 0.5 米的局数 | 620 | 686 |
| 贴身僵持超过 20 秒的局数 | 112 | 107 |
| 每局蓝方平均转向时间 | 18.12 秒 | 17.98 秒 |
| 每局蓝方落在球后方的平均时间 | 8.50 秒 | 9.20 秒 |

红方进球率降低 5.8 个百分点，但平均转向时间基本没有改变，失位后的平均落后时间反而增加。不能说“转身问题已经解决”。解围和向左推进是过程事件，发生后仍可能被红方再次抢球进门；超时和出界不自动计为防守成功。

同种子的结果也不是每局都更好：最终对照中，9 个原本蓝方进左门的开局变为红方进球。汇总和逐局结果分别见 `final-comparison.json`、`final-baseline-holdout-1000.json` 和 `final-candidate-holdout-1000.json`。

## 未改善的情况

| 其他分布，各 100 次 | 红方进球：前 → 后 | 蓝方进左门：前 → 后 |
| --- | ---: | ---: |
| 原先的随机出生方式，种子 347～446 | 63 → 64 | 33 → 32 |
| 门前矩形，种子 7000～7099 | 44 → 42 | 45 → 48 |
| 边路矩形，种子 7000～7099 | 19 → 21 | 78 → 74 |

改进集中在当前默认中场矩形，不能推广成所有出生位置都会更好。边路和旧出生方式没有改善，后续需要独立研究这些情况。本轮没有据这些最终测试结果继续调参。

## 排除的候选

- 直接追当前球位、短距离外推追球：比提前占据可达球路更容易被突破。
- 给到位后的朝向调整加入较高代价：整体并未改善，部分场景增加了转向等待。
- 贴身时立即起脚解围：起脚的静止阶段留下机会，丢球和僵持增加。
- 在截球点横向留较大偏移：经常错失脚前触球窗口，未保留。
- 总是退到更深的位置等待：增加超时和长时间僵持，未保留。

候选程序快照和 `sweep*.py`、`round*-summary.json` 保留供核对。日常程序中已移除这些失败候选的实验分支。

## 验证与交付

出生与路线的 9 项检查通过，其中检查了 5,000 个随机出生组合。浏览器检查覆盖框选、输入边界、重复种子、无效区域、批量测试、双语、手机宽度和离线导出；实时 ZIP 在独立临时目录、不同工作目录下可运行。另以默认 8 倍速进行了约 120 秒的浏览器连续运行，经历 8 个自动开局，未出现脚本异常；测试时保持浏览器在前台。

五例单文件 HTML 和 ZIP 中的两例回放按当前策略重新计算。五例分别为种子 347、350、363、351、348：两例蓝方进左门、两例红方进球、一例超时。这些是为了展示不同情况而选定的案例，不能用作成功率统计。既有 MP4/MKV 是历史视频，没有重新录制。
