# 2D 四对四调试记录 · 2026-11-19

本轮在独立的 `Four_vs_Four/` 中调试四对四。已有一攻一防目录保持原样；未修改同级 Webots 三维工程。策略调整是规则调试，不是机器学习训练。

## 入口和模型

双击根目录 `Football_4v4_Demo.html` 可看英文回放，`Football_4v4_Demo_ZH.html` 是中文回放。`Four_vs_Four/start_windows.bat` 或 `python Four_vs_Four/run.py --open` 会重新计算比赛。默认双方使用候选策略，32 倍播放，最高 128 倍。`--batch 20 --no-replay` 全速批量计算。

比赛保留 READY、SET、PLAYING、HALFTIME 和 FINISHED，默认两半场各 300 秒，计算步长 0.2 秒。标准运动速度和踢球执行时间沿用原模型。种子27完整比赛约601秒，在本机单场约1.05秒计算完成，约570倍；具体速度依机器与是否记录轨迹而异。播放速度与计算速度是两回事。

调用关系：`run.py → soccer2d.Simulation → TeamTactics.TacticalPolicy → TeamPolicy.decide → Navigation → 二维运动/球接触 → 新观测`。裁判由 MatchEngine 执行。浏览器只显示已生成的轨迹，不调用 Webots，也不重新计算 Python 决策。

## 程序分工与闭环

```text
run.py                         选择种子、红蓝策略、比赛时长、输出目录
  |
  v
soccer2d.py / Simulation        同时维护8名球员、球、接触和比赛时间
  |
  +--> MatchEngine.py           阶段、重开球、换边、比分和结束条件
  |
  +--> 每名球员读取同一时刻的 world 观测
       |
       +--> TeamTactics.py      候选策略：交接距离检查、后卫纵深
       |      |
       |      v
       +--> TeamPolicy.py       基线角色、追球、支援、带球、射门、解围
              |
              +--> DefensivePlan.py  预判防守与回追辅助
              |
              v
            Navigation.py      目标点/朝向 -> walk/turn/step/kick 等动作
              |
              v
       soccer2d.py             执行动作、计算球接触、产生下一时刻 world
              |
              +--------------------> 重复闭环直到比赛结束
              |
              v
       scene.json -> replay.html    记录 -> 浏览器查看，不参与决策
```

这是循环更新的状态决策系统，不是从追球到射门只执行一次的直线流程。每队四名球员有各自策略实例；没有 ROS 总线，Python 调用和 world 数据结构完成二维进程内的数据传递。传球意图是额外的共享观测字段，物理运动仍必须真的把球送到接球方。

## 发现和保留的改动

1. 原有传球声明可能锁住发送方和远处接球方约24秒，而当前传球的滚动距离只有约0.305米。候选策略在接球方离球超过0.60米时忽略本次交接，保留普通追球逻辑；近距离交接仍保留，且不修改共享观测。
2. 后卫处于非追球 DEFEND 状态时，改为更深的本方球门侧站位，输出 COVER_GOAL。追球、守门员、射门和重开球规则沿用基线。

改动集中在新增 `Four_vs_Four/backend/Wenao/controllers/Utils/TeamTactics.py`。基础 TeamPolicy、Navigation、MatchEngine、DefensivePlan、CourseSpecs 和 soccer2d 文件均与本轮开始时相同。

尝试过更宽的支援站位、朝向加权追球选择、前锋优先追球、重开球角色重分配、禁止远距离传球动作等组合。部分在开发种子上有利，但在验证种子上退步，因此没有加入交付策略。禁止远距离传球动作也会取消有用的短距离解围，最终只过滤不合理的交接等待。实验中的重开球目标引用旧球位置问题只属于被丢弃的实验分支，没有进入交付版本。

## 开发、验证和独立检验

开发使用110000起的8个种子；验证使用112000–112015，每个种子交换候选策略红蓝身份。最终选择于16:26:07 UTC冻结，之后才运行120000–120049的独立检验。验证中17胜5负10平的优势，没有在独立检验中同样出现。

独立检验每个种子交换颜色，共100场、50个独立开局。交换颜色的两场存在相关性，不能称为100个独立种子。基线对基线的同种子交换只改变统计标签，本身不是两条独立轨迹。

| 指标 | 基线对基线 | 候选对基线 |
|---|---:|---:|
| 胜/负/平（以被标记一方计） | 29/29/42 | 33/32/35 |
| 总进球/失球 | 117/117 | 124/121 |
| 每场开放比赛无人近球时间 | 13.02秒 | 10.20秒 |
| 每场重开球无人近球时间 | 6.76秒 | 5.97秒 |
| 每场至少三人在球周围的时间 | 25.50秒 | 27.93秒 |
| 每场最长球停滞片段均值 | 78.61秒 | 77.72秒 |
| 被标记一方重叠球员秒/场 | 80.29 | 72.07 |

无人近球指所有球员距球均超过0.65米；拥堵指至少三名球员位于球周围0.65米内。重叠球员秒是接触圆几何重叠的累计时间，不是摔倒次数。基线和候选比赛轨迹会相互影响，这些差值是整场运行比较，不能单独归因于某一个条件。

结论：候选策略减少了部分无人近球和个体重叠时间，但没有显示明显整体胜率提升，三人以上拥堵有所恶化。不可宣传为已解决多人协作或稳定战胜基线。

按种子聚类重采样10000次的平均净胜球95%区间为−0.14至0.19，包含零，不能据此声称竞争优势。原始统计与区间算法结果保存在 `comparison.json`。

另有10个新种子的候选自对弈，生成10条独立物理轨迹；统计文件按两种颜色标签记录20行，不能当成20场独立比赛。细步长0.04秒的4个种子检查用于观察数值敏感性，样本很少，不构成性能证明。相同126000–126003开局，0.2秒步长结果为5胜1负2平、进球11:7；0.04秒为5胜2负1平、进球9:7，拥堵均值26.95→44.11秒。这说明接触与决策对采样步长有敏感性，默认快速步长的结果不能当作精细物理的同一轨迹。详细数据见 `verification/four-v-four-20261119/`。

随后固定策略不再改参，使用另8个新种子127000–127007进行0.04秒步长检验、交换颜色共16场：候选6胜3负7平、进球21:18；相同种子的基线对基线进球18:18。候选比赛拥堵33.07秒，基线36.10秒；开放比赛无人近球时间候选14.98秒，基线11.24秒，反而增加。样本少且评价指标会随步长和开局变化，不能宣称修复稳定有效。

## 仍需改进

- 默认步长独立100场中，有25场候选队没有射门尝试，有27场没有传球尝试。发出动作的次数本来就不高，不能把比分和偶然碰球进门当作成熟配合。失败案例的种子和红蓝身份保存在 `failure-cases.json`。已生成种子120013的失败回放 `verification/four-v-four-20261119/failure-replay/replay.html`：红方基线1:0击败蓝方候选，拥堵约98.2秒，结果与独立测试一致。
- 接触圆模型下的密集争抢仍容易拥堵，支援与回撤需继续单独验证。
- 慢速转身和短距离传球限制依然存在；单纯调角色阈值无法变成快速多人足球。
- 下一步应先做双人近距离传接球的接触验证，再加入第三名支援球员；不能把发出 pass 命令等同于成功传球。
- 需要分别检验不同时间步长；二维数值接触轨迹不能代替三维关节、平衡、视觉和真机测试。

## 失败回放的下一步定位

种子120013的最长连续三人围球片段是563.8–601.4秒。围球期间出现的决策和动作累计帧数已记录在 `failure-crowd-diagnosis.json`；这些是多球员采样帧，不是独立事件。下一轮应在该时间段检查非持球球员何时退出近球区域，以及持球方是否存在有效的可执行射门窗口，先用同一失败种子验证，再用新种子检查副作用。

进一步复现并读取600秒时刻的实际决策：RedDefender处于CHALLENGE、向球步行；RedForwardB处于SUPPORT，目标(3.5,2.4)，在距球约0.31米处站立；BlueDefender也处于CHALLENGE，但导航正后退创造侧向对齐空间。即支援点恰好落入争球区，双方挑战与脚位调整互相牵制。详细目标、朝向和导航阶段保存在 `failure-decision-inspection.json`。这是具体失败开局的诊断，尚未验证新的通用修复。
