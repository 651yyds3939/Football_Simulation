# 被突破后原地转身的排查与修改

本页记录单独修改回防响应时的版本；后续的当前实现与验证见 [近距离封堵与断球](DEFENSIVE_CHALLENGE.md)。

## 原因

原防守球员没有独立回防状态。即使足球已经越过防守球员，策略仍请求 `INTERCEPT/CLEAR`，导航仍尝试绕到球后并对齐解围方向。`Navigator.travel()` 在角度误差大于 25° 时原地转身，随后才前进。

二维模型采用实测单项动作平均值，左转约 4.22°/s、右转约 4.34°/s；接近 180° 的转身会耗掉约 40 秒。实际 Webots 还有动作完成和站稳等待，两种环境的具体耗时不同。

## 保留的修改

- `Utils/TeamPolicy.py` 增加 `RECOVER_DEFENCE`。仅针对 defender 角色：对手距球小于 0.45 m 或球正向本方球门运动，且足球沿场地纵向超过自身 0.10 m 时，进入回防。重新回到球门侧超过 0.30 m 或威胁解除后退出。比赛停止、处罚及准备阶段清除状态。
- 回防目标为预测球位置沿本方球门方向再前移 0.55 m，预测时长 0.8 秒，目标限制在场内。它是一个局部回防点，不是已经验证的最优拦截或完整时间可达性规划。
- `Utils/Navigation.py` 增加专门导航。目标在身体后方 120°–180° 范围时直接倒退，目标在前方 ±60° 时前进；侧面目标选择较近的前进/后退轴调整方向，不总是转到能够正向行走才开始回撤。
- 浏览器增加 `Recover goal-side / 回防球门侧`、当前回防动作和状态提示，新增固定 `breakaway` 响应用例。
- 二维与 Webots 继续调用相同策略和导航模块，速度、关节动作和球的物理参数没有改变。

距离、时间和角度阈值均为策略设计假设，不是课程规定或硬件标定结果。当前没有开发边走边转的新步态，调用的仍是现有 walk/back/turn 动作。

## 固定场景对照

种子 27，足球初始位置 (1.20, 0)，红方位于 (0.95, -0.05)，三种蓝方被突破位置为 (0.75, 0.38)、(1.00, 0.35)、(0.70, 1.00)。另将场地方向镜像验证，总共六个被突破用例。保留一个蓝方仍在球门侧的位置及其镜像作为对照。

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 被突破后的首个请求 | 原地转向 | 倒退回撤 |
| 位移超过 1 cm 的时间 | 约 34.96–35.64 秒 | 0.32 秒 |
| 前 3 秒平移距离 | 0 m | 约 0.1025 m |
| 六个已失位用例最终结果 | 均在约 39.60 秒丢球 | 仍均在约 39.60 秒丢球 |
| 已在球门侧的两个对照 | 普通导航 | 保留普通导航 |

以上说明回防响应改善，不能说明追回或扑救能力提高。当前平均倒退速度约 0.0342 m/s，带球前进约 0.0853 m/s；在相同方向上已落后的球员靠倒退无法缩小差距。

## 随机开局对照

固定相同种子 47–146，共 100 次，随机开局、每轮 180 秒、guarded/centre 配置：

| 版本 | 红方进球（蓝方丢球） | 蓝方进球 | 超时 |
| --- | ---: | ---: | ---: |
| 上一版卡球修正后 | 82 | 5 | 13 |
| 本次回防响应修改后 | 83 | 5 | 12 |

只有种子 54 的结果类别从超时变为红方进球。不能将超时减少解释为防守成功率提高，本批次没有表现出防守成绩改善。

还试验过在对手控球时提前保持球门侧防线的版本，但其红方进球数升至 98 次，退守过早或站位不合适反而放走了进攻球员，因此未纳入默认代码。该版本和结果仅保留在工作区验证目录供分析。

## 三维与回归验证

新增三维固定被突破场景，使用原 `RedForwardA` 和 `BlueDefender` 控制器，其他六台移出实验。运行 12 秒后，蓝方躯干位置由 x=0.75 m 变为 x≈1.013 m，向本方球门侧移动约 0.263 m；高度和躯干摆动不同，因此该距离不能视为标定步速。

蓝方实际执行日志含 4 次 `back` 动作启动及对应站稳等待。首个倒退动作在模拟绝对时间 2.28 秒启动，之前约 2 秒为实验 SET 稳定阶段。两台机器人共 252 条实际输入记录重算一致，蓝方 4 条均请求 `RECOVERY_BACKTRACK`。

95 项单元与回归检查通过。浏览器检查验证新场景通过 Python 计算、倒退方向、中英文提示、已有遇堵让位、门前进球、批量运行和离线 HTML 回放。

尚未证明完整三维比赛防守改善、四对四站位正确或真机可用。Windows 启动脚本仍保留，未在真实 Windows 系统上实测。

## 运行

重新启动二维服务，打开新打印的网址：

```bash
bash ../2D_Shared_Policy_2026-11-11/start.sh --scenario breakaway --seed 27
```

该用例固定初始位置，主要观察反应延迟，重复运行可以得到相同结果。一般攻防用 `--scenario random`。

三维短检查，在仓库根目录运行：

```bash
python tests/run_shared_policy_webots.py --scenario breakaway --seconds 12 \
  --output runs/recovery_3d_01
python tools/check_policy_trace.py runs/recovery_3d_01
```

输出目录需为新目录。原始结果保存在工作区仓库同级的 `verification/defence-recovery-20261111/`，固定场景脚本为其中的 `check_recovery.py`，原策略和旧便携包保存在 `before/`。

后续重点是预测持球者与防守者的可达时间、提前占住有效封堵路线，以及在 Webots 中验证更快且稳定的转身和步态。当前回防状态只移除了原流程中一部分不必要等待。
