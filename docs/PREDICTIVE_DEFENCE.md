# 预判拦截与球门侧出生位置

## 当前行为

二维浏览器默认 8 倍速。倍速只改变每秒计算的仿真步数，运动速度、转向速度、触球规则和比赛结果判定均未改变。

所有内置二维开局（random、duel、lane、shot、breakaway、block）均满足：防守者位于足球和进攻者的右侧，并且到右侧球门中心 `(4.5, 0)` 的直线距离小于两者；机器人和足球不重叠。随机种子仍可重复。随机开局若横向偏移使防守者反而离球门更远，只缩小该横向偏移，不重抽有利结果。门前与斜向预设也已调整。暂停后的手动拖动属于自定义场景，可以主动构造不利位置。

## 共用策略

- `Wenao/controllers/Utils/DefensivePlan.py`：预测来球、估计路径耗时、选择拦截点。
- `TeamPolicy.py`：防守者在距球超过 0.40 m、对手距球小于 0.65 m 时，先进入 `DEFENSIVE_INTERCEPT`；近距离仍由 `CHALLENGE`、解围与遇堵逻辑处理。已经被突破时保留 `RECOVER_DEFENCE`。
- `Navigation.py`：执行拦截移动，比较侧移、转向后前进、转向后后退的耗时；覆盖目标位置后再面向来球。进入拦截状态不等于每帧都直接前进。

预测采用足球已观测到的球门方向速度；球近乎静止时，使用最近持球对手的朝向与现有平均前进速度，缺少朝向时使用通往本方球门的方向。采样最长 40 秒的轨迹，且不超过球门前边界，选取最早能够到达的覆盖位置。无可达点时选择预计迟到最少的位置，不声称必能拦下。

路径代价使用原有平均参数：前进约 0.0853 m/s、后退约 0.0342 m/s、左侧移约 0.0127 m/s、右侧移约 0.0223 m/s、保守转向约 4.22°/s。这些是已有孤立动作测量的近似值，不是课程规定或真机标定。只使用依次执行的原有动作，没有增加边跑边转或瞬间转身。覆盖球路与完成抢断是两个不同条件。

预测缓存最多约 0.4 秒，球移动超过 0.12 m 时也会重新规划。比赛阶段切换、处罚或手动重置清除相关缓存。相同观测和配置由二维与 Webots 调用同一套 Python 文件；浏览器没有独立策略。

## 相同开局的对照

开发使用种子 247–286。冻结策略后使用未参与调整的种子 347–446，各 100 局；每局 180 秒、guarded/centre、相同新出生规则、相同二维执行器。旧策略从修改前保存的便携 ZIP 加载，因此两组共享新开局，排除了“仅调整出生位置”的影响。两组 `soccer2d.py` 哈希一致。

| 指标 | 旧策略 | 预判拦截 |
| --- | ---: | ---: |
| 红方进球 | 82 | 63 |
| 蓝方进球（向左推进至对方门内） | 18 | 33 |
| 超时 | 0 | 4 |
| 蓝方独占脚部触球后向左推进至少 0.25 m 的局数 | 19 | 34 |
| 贴身后红方再度突破的局数 | 31 | 8 |
| 最长连续近球停滞超过 20 秒的局数 | 2 | 3 |
| 每局平均累计近距离纠缠 | 7.13 s | 9.51 s |

超时没有记作防守获胜。近距离纠缠指双方间距小于 0.40 m，且双方距球均小于 0.50 m；连续停滞指该状态下足球始终处于半径 0.06 m 的局部范围。独占脚部触球和推进是二维接触近似，不是已验证的控球权。

防守进球和重新推进的次数增加，突破次数减少；部分僵持变长，仍有大量失球。以上只能说明这组简化二维条件下的改善，不能用作三维或真机成功率。没有按目标胜率重抽种子、提前结束解围或自动判某方获胜。

完整对照保存在工作区 `verification/predictive-defence-20261111/`：`before/`、`baseline-validation-100/metrics.json`、`final-validation-100/metrics.json` 和 `comparison.json`。旧的统计使用不同开局和版本，应按哈希与种子区分。

## 验证

113 项单元与回归检查通过，包括 5000 个随机种子和全部预设的出生位置约束、预测点、不可达情况、镜像方向、动作代价和重置。浏览器检查覆盖默认 8 倍、预判状态中英文显示、实时运行、拖动、批量测试与离线回放。

24 秒 Webots 固定拦截用例中，原来的两个物理控制器运行；蓝方实际执行前进、侧移和转向。446 条实际输入记录经共用模块重算完全一致，蓝方其中有 67 条预判拦截请求。这个检查验证接口和调用，不能证明长期不摔倒、必能抢断或轨迹与二维一致。

```bash
python tests/run_shared_policy_webots.py --scenario intercept --seconds 24 \
  --output runs/predictive_intercept_3d_01
python tools/check_policy_trace.py runs/predictive_intercept_3d_01
```

便携包的 `defence_replay.html` 使用随机开局种子 355，展示一次预判、防守和后续推进；`example_replay.html` 使用种子 347，展示一次进攻成功。二者是离线回放，不代表总体胜率。更新后必须停止旧 Python 服务并重新启动，浏览器刷新不会重载旧进程已经导入的模块。

## 运动与硬件限制

当前二维执行器只执行单个行走、后退、侧移或转向动作，转向时没有主动平移；Webots 使用独立的 `.motion` 关节轨迹，普通转向通常完成后才能切换。统一的边走边转步态尚未实现。这会使防守者在调整朝向期间丢失拦截窗口，尤其是横向偏移较大或已经被突破时。预测与近球策略仍有不足，不能将全部失球归因于动作速度。

二维各左转动作共用约 4.22°/s、各右转动作共用约 4.34°/s 的近似速率，未分别覆盖不同三维转向动作的表现。按左转近似转 90° 约需 21 秒；若对手同期以约 0.085 m/s 持续前进，可推进约 1.8 m。这是简化模型中的推算，不是实验室 NAO6 的实测值。播放倍速不改变该时间关系。

实验室 NAO6 的固件、接口、实际步态和转向性能尚未验证。NAOqi 官方 `moveToward(x, y, theta)` 允许组合平移和旋转速度输入，不能把当前执行器的动作互斥概括为硬件无法边走边转。[官方接口说明](https://doc.aldebaran.com/2-5/naoqi/motion/control-walk-api.html)

后续先测量各转向动作，再在 Webots 中验证统一步态的速度、转弯半径、动作过渡和跌倒情况，最后将验证后的参数同步到二维。当前版本适合作为阶段性的策略测试原型，尚不代表完整三维比赛或真机性能验收通过。
