# 2D 四对四：无球配合与协作测试 · 2026-11-19

本轮从上一轮 `Four_vs_Four/` 出发，重点检查“双方各一人争球，其余球员只看着”的现象。仅调整二维四对四；已有1v1目录和同级Webots三维项目不修改。全部为规则策略调试，不是机器学习训练。

## 发现的具体原因

- 一名前锋采用固定的球前方、侧方支援点，目标有时落入争球区；到点后保持位置，形成围堵。
- 后卫的纵深限制承担防守保险。直接取消限制、让后卫大幅跟随进攻，会明显增加失球。因此不能用“所有人都动起来”作为优化目标。
- 无球队员若只允许先转身再走，在当前慢速转身模型中容易长时间调整朝向。接应点随球持续移动时，又可能不断改方向。
- 一次传球的模型滚动距离约0.305米，踢球动作约3.299秒。远处队友无法像正常足球那样迅速接球，传球意图和实际接触必须分开验证。

## 保留的候选改动

1. **有球时搜索接应点**：无球前锋不再只使用一个固定支援点。球队有最近触球且本方球员在球附近时，从球周围六个有边界限制的候选点中，综合预计到达时间、对手距离、传球线路和队友间距选点。球的短期预测最多延伸0.5米，不移动真实足球。
2. **短暂保持目标**：接应点保持最多4秒；球明显移动、局面变化或时限到达后再选择，减少因细小球晃动反复转向。
3. **局部让位**：非追球球员进入近球争抢区域时，给实际追球者留出空间，采用进入与退出距离不同的阈值，减少反复进出。
4. **按现有动作成本补位**：新无球状态可以比较走、退、侧移、转身后再走的预计耗时，选择已有动作；不增加速度，不同时旋转和行走。
5. **保守短传与接球准备**：只考虑距离约1.05米以内、双方朝向满足限制、对手压力和线路条件合适的指定队友。发送方的朝向变化有界；接球方先准备，只有执行器实际触球后才进入接球阶段。踢空会取消等待；重开球、未释放、受罚或消息超时不会覆盖原有阶段和处罚行为。球仍按原约0.305米滚动距离运动，接球队员必须实际移动接触足球。
6. **保持职责**：普通追球者、持球处理、守门员和后卫纵深仍沿用上一轮。门将保持防线、后卫保护后方属于有效分工，不以持续跑动作为成功标准。

此次修改没有提高踢球力量，没有更改球运动、接触裁决、机器人动作速度或比赛计时。基础 `TeamPolicy.py`、`Navigation.py` 和 `MatchEngine.py` 与本轮开始时相同；`soccer2d.py` 仅增加短传消息的准备/释放标记，以及踢空后取消等待。AST检查去掉这些消息处理后与原模拟器一致。新行为通过独立策略及导航子类实现；换边摆阵后仍重新安装候选导航。

## 运行程序

```text
run.py
  -> TeamNavigation.TeamSimulation：完整四对四比赛
     -> TeamTactics.TacticalPolicy：接应搜索、目标保持、局部让位
        -> TeamPolicy：原角色、追球、带球、射门和解围
     -> TeamNavigation.CooperativeNavigator：新无球状态的补位动作
        -> Navigation.Navigator：原攻击及其他动作执行
     -> soccer2d：实际运动、球接触和下一时刻观测
     -> MatchEngine：比赛阶段、重开球、换边和比分
  -> scene.json -> replay.html：离线回放，不参与决策
```

`PreviousTactics.py` 保存上一轮策略用于对照。运行参数 `coordinated` 为本轮策略，`previous` 为上一轮策略，`baseline` 为基础TeamPolicy。默认双方均为本轮策略；自对弈比分不用于证明优于旧策略。根目录展示回放的红队为上一轮、蓝队为本轮，采用验证种子212001和212006，均真实出现一次指定队友接球；并非随机抽样成功率。

## 验证方法与未采用的方案

开发种子210000–210007；验证种子212000–212015。每个种子交换候选队红蓝身份，两场之间存在相关性。选型后冻结源码，再运行新种子的独立检验，不能将交换颜色的100场称为100个独立开局。

开发中的接应搜索候选取得7胜0负9平；整理后的版本复现全部32场验证比分，为13胜8负11平、进球43:39。开发成绩不作为最终性能结论。

没有采用：后卫大幅前压、强制将接球队员拉到球边、长时间换人接管争球、强制短传。它们有时让更多人参与，或者产生了更多接球，但通常降低攻防效果或加重拥堵。没有为使结果好看而放宽接触、扩大传球距离或降低对手能力。

短传专项采用两名红队球员和一名静止蓝队阻挡者的声明测试场景。某个未采用的近距离协作候选在相同几何位置的20个踢球噪声种子中，出现20次指定队友接触，并有对应的接球队员脚下推动记录。这只说明该简单模型里短传能够执行，不能称为20个独立比赛或正式版本的传球成功率。正式4v4中的强制短传候选，在验证中取得7胜12负13平，拥堵约76.7秒/场，未采用。

## 判读边界

- 无球移动时间多不等于更会配合；必须同时检查比分、拥堵、失去防守保护及无人近球时间。
- `pass_attempts` 包括开球和解围；只有带指定receiver的动作才计作定向传球尝试。指定队友接触、接球队员脚下接触和实际可控的连续配合仍是不同标准。
- 二维使用精确位置和简化圆形接触，没有相机误差、关节平衡、摔倒和真实硬件。因此结果仅用于筛查策略，需要后续三维及实物验证。

## 独立结果与取舍

先冻结无短传的接应搜索候选，用214000–214049的50个新种子交换颜色共100场：34胜31负35平、进球131:126；对照旧策略自对弈进球128:128。拥堵25.62→19.98秒，无球移动占比33.51%→37.27%，但开放比赛无人近球10.48→12.12秒。身体重叠球员秒70.56→73.95/场反而增加，不能把拥堵减少说成碰撞问题已解决。

随后加入按朝向、压力、接球准备限制的短传，并在比赛阶段保护的实现检查后继续测试，结果分开记录：

| 测试 | 新种子/场次 | 胜/负/平 | 进球/失球 | 定向尝试/指定队友接触/脚下接触确认 |
|---|---|---|---|---|
| 带短传候选，218000–218049 | 50/100 | 31/32/37 | 125/126 | 12/11/10 |
| 最终阶段保护版，222000–222029 | 30/60 | 22/22/16 | 78/76 | 6/6/6 |
| 带短传候选，步长0.04秒，220000–220007 | 8/16 | 3/6/7 | 16/19 | 0/0/0 |

100场候选的拥堵25.55秒，对照同种子旧策略自对弈20.97秒，反而增加。最终60场为24.96秒，对照26.41秒，略有减少。细步长测试拥堵26.30秒、对照41.77秒，但候选只有3胜6负7平，并未展示稳定竞技优势。不能把不同种子的指标拼起来宣传全面改善。

“指定队友接触”包括简化接触代理；“脚下接触确认”还要求相同接球时刻出现该接球队员的foot_control_change事件。这仍不是经过三维/真机验证的传球，也不能从几次成功推导可靠传球成功率。最终60场不是60个独立种子；两个实现只相差接球准备的阶段/处罚/时效保护，分别冻结和记录，不合并为一个完全相同源码的160场结果。

**结论：无球队员开始采用有目的的接应和局部让位，并出现少量可执行的队友短传；胜率仍接近旧版，未解决稳定传接球和多人拥堵。** 默认采用有阶段保护的配合版本，旧策略仍可通过previous参数对照。无短传搜索候选保存在本轮verification/selected-app，作为回退和后续消融依据。

下一步应先扩大“朝向合适的短传—接球—下一动作”专门测试，减少接球后重新转向耗时；并分析低进攻参与度的种子。不能通过强制全员追球、任意提高运动速度或扩大未校准的传球距离来掩盖限制。

## 成功接触之后仍有问题

两个展示回放都出现了接球队员实际脚下接触：英文例从踢到球至接球约9.6秒，中文例约6.4秒。但接球后接球队员仍在转向：随后15秒球几乎没有向球门推进；英文例约20秒后对方再触球。这说明“接到球”还不是“形成有效连续进攻”。详细数据在 `pass-followup.json`，没有把裁判放球当作推进量。下一轮应优先解决接球朝向与下一动作的衔接，而非继续增加传球次数。

接球瞬间，相对球门方向的朝向误差分别约108.2°与117.0°；按当前转向率、允许12°余差粗估，仅转向就需约22.2秒和24.9秒，不包括脚位调整、避障和争球。该估计解释了接球后停滞，并非测得真机时间。
